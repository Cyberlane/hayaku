How it works

From a code change to a clear plan.

See what changed, which tests may be affected, and why Hayaku recommends a particular run.

01 ↗

Compare two commits

Hayaku reads the code before and after your change. Deleted files and renamed code stay part of the picture.

02 ↗

Review the recommendation

See which tests may be affected, the commands to run, and anything Hayaku could not establish. Missing information keeps the full suite or stops planning.

03 ↗

Compare with a full run

Use shadow mode to check experimental recommendations against a separate full test run. Your original test suite remains required.

Handling uncertainty

When something is unclear, include more tests.

Code can read files, call services, or share state that dependency lists do not show. Hayaku makes those gaps visible and keeps your full test run in place.

How Hayaku decides what to run →

Result reuse · WASI suites only

Same inputs. Reuse the passing result.

A WASI suite runs as WebAssembly with controlled inputs and restricted access to your computer. Hayaku can reuse its verified passing result when the code, inputs, and execution settings match.

This is a separate test suite. It does not replace your normal Go, JavaScript, Python, browser, or service tests.

Get started

Try Hayaku in your repository.

Download Hayaku for your platform and check the file against the release checksum. Then create a configuration, review the test commands, and compare two commits.

Follow the setup guide →
In your repository
# Generate and review hayaku.json
hayaku init
hayaku doctor

# Compare two commits already on your computer
hayaku plan --base BASE --candidate HEAD \
  --output .git/hayaku-plan.json
hayaku explain --plan .git/hayaku-plan.json

Replace BASE with the commit to compare against. Planning reads committed code. Inspecting tests can execute project code, so use a repository you trust.
